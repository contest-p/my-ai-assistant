## MCP 인증 검토

`SharedSecretAuthMiddleware`는 비밀키 미설정·불일치 시 401로 거부하며 `/mcp`에만
적용된다. FastAPI lifespan에서 MCP session manager를 실행하는 구조는
[SDK의 ASGI 연결 안내](https://py.sdk.modelcontextprotocol.io/run/asgi/)와 부합한다.

쿼리 비밀키는 노출 위험을 감수한 우회 구현이다. HTTPS가 서버 로그까지 숨기지는 않는다.
로컬 `backend/uvicorn3.log`에 `?key=`가 있는 요청 기록을 확인했고, 설치된 uvicorn의
`get_path_with_query_string`도 쿼리를 접근 로그용 경로에 포함한다. 실제 키 값은 감사
출력에 표시하지 않았다. Render의 로그 보관·열람 권한까지는 확인하지 못했다. 커넥터
설정, URL을 붙여 넣은 대화·스크린샷·명령 이력도 노출 경로가 될 수 있다.

[MCP 인증 명세](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)는
OAuth access token을 URL 쿼리에 넣지 않도록 규정한다. 현재 공유키 방식은 그 표준
인증 구현으로 간주할 수 없다. 이 사실만으로 OAuth 도입을 결정하지는 않는다.

더 큰 문제는 기존 `/api/data`, `/api/conversations`, `/api/chat`에 인증 검사가 없다는
점이다. 이 코드가 배포됐다면 MCP 키 없이도 소비·대화를 읽거나 수정·삭제하고 AI 호출을
발생시킬 수 있다. CORS는 사용자 인증이 아니며, 서버 간 요청을 차단하지 않는다.
따라서 “개인용 조회 전용 도구라 안전하다”는 설명은 전체 앱에는 맞지 않는다.

우선 공유된 로그·URL 여부를 확인하고 노출된 실제 키는 사용자 측에서 교체하는 것이
좋다. 접근 로그의 쿼리 제거와 앱 전체 접근 정책은 별도 승인 후 결정한다. 프론트
정적 JS에 공용 비밀키를 넣는 것으로는 해결되지 않는다. 이번에는 인증 방식을 바꾸거나
Render 설정·키를 수정하지 않았다.

[Claude 공식 안내](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)는
Free 커넥터 1개 제한을 명시한다. 하지만 검토한 페이지에서는 개인 플랜의 static_headers
지원 여부를 확정할 근거를 찾지 못했다. “조직 전용이라 개인은 불가능”과 “쿼리 방식이면
모든 플랜에서 항상 된다”는 단정은 확인된 사실로 취급하지 않는다.

## Firestore 쿼터와 캐싱

[공식 한도](https://firebase.google.com/docs/firestore/quotas)는 읽기 50,000건/일이며
태평양시간 자정 무렵 초기화된다. 9월의 한국시간으로는 약 16시, 표준시 기간에는
약 17시다. 현재 회복 여부는 확인하지 않았다. 로컬 로그의 ResourceExhausted 429는
확인했지만 메시지 자체만으로 읽기·쓰기 중 어느 한도가 소진됐는지 특정할 수 없다.
Task의 과거 기록은 “쓰기”, 인수인계는 “읽기”라고 달라 콘솔 사용량 대조가 필요하다.

1,116건이 유지되고 다른 읽기가 없다는 가정의 산술 추정:

| 행동 | 거래 문서 읽기 |
|---|---:|
| summary 1회 또는 MCP tool 1회 | 1,116 |
| 채팅 1회 + tool 1회 | 2,232 + 대화 관련 읽기 |
| 필터 없는 거래 목록 페이지 1회 | 1,116 (페이지 크기는 반환량만 줄임) |
| 전체 조회 44회 / 45회 | 49,104 / 50,220 |
| 도구 1회 쓰는 채팅 22회 | 49,104 + 대화·화면 조회 |

반복 가능한 설계 문제다. 테스트 집중은 촉발 요인이지만 개인 사용자도 수십 번의
질문·페이지 이동으로 한도를 소진할 수 있다. 모델이 한 번에 여러 tool_calls를 만들면
각 호출이 다시 전체를 읽으므로 비용은 더 커진다.

30~60초 TTL만으로 “매 요청마다 최신”을 보장할 수는 없다. 기간 내 수정이 다음 요청에
반영되지 않고, 1분 넘는 간격의 사용에는 캐시 효과도 작다. 권고 순서는 다음과 같다.

1. 범위가 정해진 도구 조회는 Firestore에서 날짜·분류로 필터링하고 해당 범위 전체를
   읽기: 조회 시 최신성 유지. 기본 전체 summary에는 전체 컬렉션 재조회 유지.
2. 목록은 데이터베이스 페이지 조회·count 집계로 변경 검토: 응답 계약을 유지하되
   현재 메모리 페이지네이션의 전체 읽기를 줄임. count 집계 자체도 무료 읽기는 아님.
3. 한 채팅 요청 안에서 이미 읽은 데이터를 도구와 공유할지 결정: 요청 간 캐시는
   아니지만 요청 도중 갱신에 대한 의미가 달라지므로 PRD 확인 후 적용.
4. TTL은 최신성의 정의를 “CRUD 직후 무효화, 외부 변경은 최대 TTL 지연”으로 바꾸는
   경우에만 검토. 모든 쓰기 경로·여러 프로세스가 있으면 추가 고려가 필요함.

PRD 13-1·Task 3.6의 현재 원칙을 바꾸는 결정을 임의로 하지 않았으며 캐싱은 추가하지 않았다.

## 빈 답변·reasoning 진단

`5bb50e6`에 500/1200 예산 분리와 fallback이 실제로 커밋되어 있다. `stream`은
미지정(기본 False)이므로 앱에 스트리밍 조립 코드는 없다. 다만 이를 근거로 프록시
내부 변환 문제까지 배제할 수는 없다. 현재 코드는 finish_reason·usage를 기록하지
않으며, 로컬 로그에도 이를 입증할 필드가 없어 reasoning 과소 예산은 유력 가설이다.

[OpenAI reasoning 안내](https://developers.openai.com/api/docs/guides/reasoning)는
출력 전에 reasoning이 예산을 소진할 수 있음을 설명한다.
[GPT-5.5 공식 모델 안내](https://developers.openai.com/api/docs/models/gpt-5.5)는
none/low/medium/high/xhigh와 기본 medium을 명시한다. 다만 코디세이 프록시가 같은
설정을 전달·지원하는지는 별도로 확인해야 한다.

더 나은 진단은 같은 합성 summary·질문을 고정하고 호출 단계, 반환 model, request ID,
지연, finish_reason, content 길이, tool 수, completion_tokens 및 reasoning_tokens를
비밀정보 없이 기록하는 것이다. 이때 Firestore를 반복 조회할 필요가 없다.
프록시 지원을 확인한 후 reasoning_effort=low와 현재 설정을 비교하고, 그 다음 출력
예산만 변경해 비교한다. 한 번에 여러 설정·모델을 바꾸지 않는다. Chat Completions의
max_completion_tokens 지원·기존 max_tokens 변환도 프록시 제공자에게 확인한다.

현재 루프는 도구 호출뿐 아니라 빈 응답 재시도도 3회에 포함하고, 마지막 호출까지
총 4회 요청할 수 있다. 앱 지정 예산의 합은 500+1200+1200+1200=4100이며, SDK 재시도와
입력 토큰은 별도다. 같은 부족한 예산으로 여러 번 반복하면 비용만 늘 수 있다.
fallback은 오류 안내이지 질문 5의 성공이 아니다. 질문 5의 “알려진 이슈 문서화”는
현재 PRD에 없으며 기대 동작만 있다. 이번 감사에서는 모델 설정·재시도 정책을 변경하지 않았다.
