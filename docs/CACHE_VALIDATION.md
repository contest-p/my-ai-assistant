## 선택한 방식

약 1,116건 전체 거래를 프로세스 메모리에 3,600초 보관한다. 빠른 조회·채팅·요약·목록·
내보내기는 모두 `fetch_all_data()`를 사용한다. 기간 필터·정렬·페이지 처리는 메모리에서
수행한다. 기존 계산/응답 형식과 null·사용자 분류를 유지한다. Redis나 추가 서비스는 없다.
주로 고정된 과거 거래를 동료평가 중 반복 탐색하는 규모에서 변경 범위와 운영 부담이 작다.
1시간이면 짧은 TTL보다 페이지·월 이동 사이에도 재사용 가능하고, 앱 CRUD는 즉시 무효화한다.

- TTL은 성공적으로 로드한 시각부터 측정하며 접근으로 연장하지 않는다. 빈 정상 결과도 캐시한다.
- 동기 FastAPI 경로가 프로세스 공통 RLock을 사용한다. 캐시 확인·로드·거래 쓰기를 직렬화한다.
  먼저 시작한 읽기는 변경 전 값을 받을 수 있지만, 쓰기가 끝난 뒤 시작한 읽기는 이전 캐시를
  사용할 수 없다. 쓰기 중 이미 진행 중인 응답의 값을 소급 변경하지는 않는다.
- 쓰기 성공 직후뿐 아니라 예외 종료도 캐시를 무효화한다. 쓰기는 완료됐으나 응답용 get이
  실패한 상황도 포함한다. 초기 적재 함수는 같은 프로세스에서만 무효화가 적용된다.
- 반환 데이터는 깊은 복사로 분리하므로 정렬·필터·수정으로 공용 캐시가 훼손되지 않는다.
- 전체 거래 stream은 `retry=None`, RPC timeout 15초. 부분 결과 후 실패도 전부 폐기한다.
  원본 예외를 응답에 노출하지 않고 503·한국어 안내·Retry-After를 반환한다.
- 실패 후 60초 동안 오류 상태를 공유하고 DB를 재호출하지 않는다. 자동 재시도나 백그라운드
  조회는 없다. 그 이후 사용자 요청이 있을 때 1회 시도한다. 오류 대기는 CRUD로 해제하지 않는다.
  한도 초과라면 한도 회복이 필요하다는 안내를 표시한다. 60초가 한도 초기화 시간은 아니다.
- summary의 generated_at은 계산 시각이며 Firestore 재조회 시각을 뜻하지 않는다.

## 읽기 감소

데이터 변경·만료·프로세스 재시작이 없는 한 번의 캐시 수명에서 전체 거래 소비 요청 N회는
기존 약 `1,116 × N`건에서 `1,116`건으로 줄어든다. 100회는 111,600 → 1,116건(99% 감소).
목록에 DB 날짜 필터가 있던 경우 이전 읽기 수는 해당 범위 건수이므로 이 산식과 다르다.

대화 조회/저장 응답용 읽기, CRUD 존재 확인/응답용 읽기, 다른 클라이언트 사용량은 별도다.
수정이 잦으면 매 수정 후 전체 재로딩하므로 절감률은 낮아진다. 실패한 부분 읽기도 과금될 수 있다.

## 로컬 검증

`backend/scripts/check_transaction_cache.py`는 pytest 없이 실행하는 검증 스크립트다.
설치된 프로젝트 의존성 환경에서 저장소 루트의 `python backend/scripts/check_transaction_cache.py`
또는 backend 안에서 `python scripts/check_transaction_cache.py`로 재현한다.
config를 먼저 가짜 모듈로 주입하므로 .env/서비스 계정 초기화를 실행하지 않는다.
DB는 합성 1,116건, AI와 대화 저장은 가짜 구현이다. 외부 소켓 연결을 차단하며 Windows
이벤트 루프의 내부 loopback 연결만 허용한다. 실제 Firestore/AI 호출·데이터 변경은 없다.

확인 결과:

- 100회 혼합 요청(요약·목록·빠른 조회·JSON 내보내기·채팅): stream 1회, 문서 1,116건.
- TTL 경계 3,600초의 32개 동시 요청: 추가 stream 1회. 반환 데이터 변조는 캐시에 영향 없음.
- 추가·수정·삭제 후 재조회, 최신월 변경, null·사용자 분류 유지, 없는 거래 404.
- 조회를 중간에 정지한 채 수정 요청을 겹치게 한 후 다음 조회에서 변경값 확인.
- DB 쓰기 완료 후 응답 읽기 실패에도 캐시 무효화.
- 한도/일반 DB 오류를 부분 stream 중 발생시킨 24개 동시 요청: DB 시도 1회.
  네 조회 경로와 채팅에서 503, 내부 오류 비노출, AI 미호출, 60초 후 복구.
- 비어 있는 캐시에서 한도 초과·반복 요청 억제·복구, 실제 정상 빈 DB 결과 캐시.
- 채팅 저장 실패 후 1회 재시도 성공 200, 최종 실패 500, 없는 대화 404, 기존 대화 이어가기.
- backend Python 구문 검사 및 git diff 공백 검사. 프론트 화면 자체의 새 브라우저 검증은 수행하지 않음.
- Node에서 기존 api.js에 가짜 503 응답을 주입하여 빠른 조회·채팅·다운로드가 한국어 오류를
  전달하고 자동 재시도하지 않는 것을 확인했다.

검증 의존성은 `.local-validation/`에 격리 설치하고 Git 제외했다. 제품 requirements는 변경하지 않았다.

## 운영 한계와 배포 검증

문서상 Render는 worker 옵션 없는 `uvicorn main:app --host 0.0.0.0 --port $PORT`다.
이 구현은 인스턴스 1개·프로세스 1개 운영에 맞춘 것이다. 실제 대시보드 설정은 이번에
조회하지 않았으며 배포 검증도 하지 않았다. 다중 worker/인스턴스는 각자 조회하고 무효화도
전달되지 않는다. 그 구성으로 확장할 때 공유 캐시나 조회 구조 재검토가 필요하다.

서버 재시작·절전 후 재기동은 캐시를 없애며 다음 요청은 전체를 다시 읽는다.
콘솔이나 별도 프로세스의 적재/수정은 최대 1시간 뒤 반영된다. 즉시 반영이 필요한 외부 작업은
별도 운영 절차가 필요하다. 로드/쓰기 중 다른 거래 요청이 기다리는 것은 단순 잠금의 절충점이다.
이미 소진된 Firestore 할당량은 코드 변경으로 복구되지 않으며 캐시가 비어 있으면 DB 읽기가
성공할 때까지 조회를 제공할 수 없다. 이번 로컬 성공은 실제 운영 한도 회복이나 배포 성공의 증거가 아니다.
